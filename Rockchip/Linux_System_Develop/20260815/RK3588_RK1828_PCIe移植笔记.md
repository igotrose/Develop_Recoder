# RK3588 + RK1828 PCIe/RKNN3 移植笔记与总结

## 1. 目标与最终结果

本文记录将 RK1828 PCIe AI 协处理器集成到 RK3588 Linux 5.10.198 SDK 的过程。

最终验证结果：

- RK3588 作为 PCIe Root Complex；
- RK1828 枚举为 `1d87:182a`；
- 新版 `pcie-rkep` 驱动内置进内核并成功绑定；
- 自动创建 `/dev/pcie-rkep-0000:01:00.0`；
- systemd 冷启动时自动下载 RK1828 固件；
- `rknn-smi info` 显示 RK1828 Online、Health OK；
- RK1828 板载内存为 5120 MB；
- 当前 PCIe 链路协商为 Gen2 x1。

验证输出示例：

```text
| Device  Status | Health | Chip   | Bus-Id       | Memory-Usage(MB) |
| 0       Online | OK     | RK1828 | 0000:01:00.0 | 32 / 5120        |
```

## 3. 原始问题

RK1828 最初能够被 PCIe 枚举：

```text
0000:01:00.0 Processing accelerators [1200]:
Rockchip Electronics Co., Ltd Device [1d87:182a]
```

但是：

- 没有驱动绑定；
- 没有 `/dev/pcie-rkep-*`；
- `rknn-smi info` 报 `Failed to initialize rknnsmi`。

板端配置实际已经启用旧驱动：

```text
CONFIG_PCIE_FUNC_RKEP=y
```

问题在于旧驱动的 PCI ID 表只支持：

```c
{ PCI_VDEVICE(ROCKCHIP, 0x356a), 1 },
```

而 RK1828 的 Device ID 是 `0x182a`，因此不会触发 probe。

RK182x SDK 新驱动包含：

```c
{ PCI_VDEVICE(ROCKCHIP, 0x356a), 1 },
{ PCI_VDEVICE(ROCKCHIP, 0x182a), 1 },
```

## 4. 增加 Rockchip PCIe PM Control 接口

新版 RK1828 驱动调用：

```c
rockchip_dw_pcie_pm_ctrl_for_user(
	pcie_rkep->pdev,
	ROCKCHIP_PCIE_PM_CTRL_RESET);
```

原 SDK 内核没有该接口，因此先按顺序移植 Rockchip 官方 `develop-5.10` 的两个提交。

### 4.1 新增接口

```text
bb9632320ba730395891d0e645b273804baf1533
PCI: dw: rockchip: Support rockchip_dw_pcie_pm_ctrl_for_user
```

官方下载：

```bash
curl -L \
  https://github.com/rockchip-linux/kernel/commit/bb9632320ba730395891d0e645b273804baf1533.patch \
  -o /tmp/0001-rockchip-pcie-pm-control.patch
```

检查并应用：

```bash
cd kernel
git apply --check /tmp/0001-rockchip-pcie-pm-control.patch
git am /tmp/0001-rockchip-pcie-pm-control.patch
```

### 4.2 修复 reset 期间的 IRQ 问题

```text
d3f96b380eea087451330f173021c1b5ad5f74bf
PCI: rockchip: dw: Mask and unmask misc irq
```

该补丁避免 controller suspend/resume 尚未完成时 IRQ handler 访问 DBI 导致系统挂死。

```bash
curl -L \
  https://github.com/rockchip-linux/kernel/commit/d3f96b380eea087451330f173021c1b5ad5f74bf.patch \
  -o /tmp/0002-rockchip-pcie-mask-unmask-irq.patch

git apply --check /tmp/0002-rockchip-pcie-mask-unmask-irq.patch
git am /tmp/0002-rockchip-pcie-mask-unmask-irq.patch
```

本地对应提交：

```text
77707595b3fe PCI: dw: rockchip: Support rockchip_dw_pcie_pm_ctrl_for_user
c9593339e403 PCI: rockchip: dw: Mask and unmask misc irq
```

最终代码位置：

```text
kernel/include/linux/aspm_ext.h
kernel/drivers/pci/controller/dwc/pcie-dw-rockchip.c
```

需要确认以下内容存在：

```c
ROCKCHIP_PCIE_PM_CTRL_RESET
rockchip_dw_pcie_pm_ctrl_for_user()
EXPORT_SYMBOL(rockchip_dw_pcie_pm_ctrl_for_user);
```

## 5. 用 RK182x SDK 新驱动替换内核旧驱动

### 5.1 替换文件

从 RK182x SDK 更新以下 4 个文件：

```text
driver/linux/pcie-rkep/pcie-rkep.c
    -> kernel/drivers/misc/rockchip/pcie-rkep.c

driver/linux/pcie-rkep/rk-pcie-ep.h
    -> kernel/include/uapi/linux/rk-pcie-ep.h

driver/linux/pcie-rkep/pcie-dw-dmatest.c
    -> kernel/drivers/pci/controller/dwc/pcie-dw-dmatest.c

driver/linux/pcie-rkep/pcie-dw-dmatest.h
    -> kernel/drivers/pci/controller/dwc/pcie-dw-dmatest.h
```

SDK 的 `rockchip-pcie-dma.h` 与当前内核版本相同，无需替换。

### 5.2 将独立 KO 源码改回内核内置形式

RK182x SDK 目录中的驱动按独立 `.ko` 方式组织，直接复制进内核会重复包含 `pcie-dw-dmatest.c`。内置驱动需要进行以下调整。

在 `pcie-rkep.c` 中使用内核头文件路径：

```c
#include <uapi/linux/rk-pcie-ep.h>
#include "../../pci/controller/rockchip-pcie-dma.h"
#include "../../pci/controller/dwc/pcie-dw-dmatest.h"
```

删除：

```c
#if 1 /* Always built-in for standalone KO */
#include "pcie-dw-dmatest.c"
#endif
```

在 `pcie-dw-dmatest.c` 中恢复内核相对路径：

```c
#include "../rockchip-pcie-dma.h"
```

在 `pcie-dw-dmatest.h` 中恢复 Kconfig 条件：

```c
#if IS_ENABLED(CONFIG_PCIE_DW_DMATEST)
```

### 5.3 内核配置

在 `rockchip_linux_defconfig` 中启用：

```text
CONFIG_PCIEASPM_EXT=y
CONFIG_PCIE_FUNC_RKEP=y
CONFIG_PCIE_DW_DMATEST=y
```

本次采用内置驱动，因此不再单独安装 `pcie-rkep.ko`。

新版驱动本地提交：

```text
727e579a3e81 PCI: rockchip: update RKEP driver for RK1828
```

驱动版本：

```text
DRV_VERSION = 0x00030300
```

## 9. 关键问题和排查结论

### 9.1 `rknn-smi` 初始化失败

症状：

```text
Failed to initialize rknnsmi
```

检查顺序：

```bash
lspci -nn
readlink /sys/bus/pci/devices/0000:01:00.0/driver
ls -l /dev/pcie-rkep-*
systemctl status rknn3
dmesg | grep -i -E 'pcie-rkep|rkep|182a'
```

本次最初原因是旧驱动不匹配 Device ID `0x182a`。

### 9.2 `Device boot state: 0xffffffff`

症状：

```text
Device boot state: 0xffffffff
Mode=Unknown
Device is not in maskrom mode or loader mode
```

原因：烧录新内核后只重启了 RK3588，RK1828 M.2 没有完全掉电，Endpoint 保留了旧的异常状态。

解决方法：

1. 关闭整机；
2. 拔掉电源；
3. 等待至少 10 秒；
4. 重新上电冷启动。

仅执行 host reboot 不一定会切断 RK1828 M.2 电源。

### 9.3 运行中不要直接 restart 服务

RK1828 固件已经运行后，设备不再处于 MaskROM/Loader。此时执行：

```bash
sudo systemctl restart rknn3
```

启动脚本会再次尝试下载固件并失败：

```text
Device is not in maskrom mode or loader mode
```

正常使用只需：

```bash
systemctl status rknn3
sudo rknn-smi info
```

需要重新加载固件时采用整机冷启动。后续可以改造 `rknn3_startup`，使其检测设备已 Online 时跳过重复下载。

### 9.4 为什么链路只有 Gen2 x1

RK3588 Root Port 上报：

```text
LnkCap: Speed 8GT/s, Width x4
LnkCtl2: Target Link Speed: 8GT/s
```

RK1828 Endpoint 当前上报：

```text
LnkCap: Speed 5GT/s, Width x1
LnkCap2: Supported Link Speeds: 2.5-5GT/s
LnkSta: Speed 5GT/s, Width x1
```

最终链路取两端能力交集，因此协商为 Gen2 x1。修改 RK3588 的 `max-link-speed` 不能强制 Endpoint 运行 Gen3。

## 10. 模型、内存和存储

RK1828 设备内存：

```text
5120 MB
```

该内存独立于 RK3588 Host RAM 和 eMMC 存储。

RK3588 eMMC：

```text
总容量约 57.6 GiB
/          约 14 GiB
/userdata  约 43.3 GiB
```

模型文件建议存放：

```text
/userdata/models/
```

运行时监控：

```bash
watch -n 1 'sudo rknn-smi info'
watch -n 1 free -h
```

大致建议：

- MobileNet、ResNet、YOLO 等 CNN 通常占用数百 MB 到 1 GB；
- 0.5B/0.6B 量化 LLM 建议预留 1～2 GB；
- 1.5B/1.7B 量化 LLM 建议预留 2～3 GB；
- 3B/4B 量化 LLM 可能占用 3～5 GB；
- 7B/8B 在 5 GB 设备内存上比较紧张，通常需要流式权重、较短上下文或其他优化。

实际占用还包括 KV Cache、中间张量、Runtime 工作区和并发 session。

## 11. 后续打包建议

当前驱动采用内核内置方式，后续 Debian 包只需要安装用户态 Runtime、固件、服务和工具，不需要携带 `.ko`。

建议拆分：

```text
rk182x-runtime_<version>_arm64.deb
rk1828-m2-firmware_<version>_all.deb
```

如果未来改成外置模块，再增加与内核版本严格绑定的包：

```text
rk1828-pcie-driver-5.10.198_<version>_arm64.deb
```

外置 `.ko` 必须与目标内核的 kernel release、配置、工具链和 `Module.symvers` 匹配。
